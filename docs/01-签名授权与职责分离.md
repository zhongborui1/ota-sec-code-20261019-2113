# 签名授权与职责分离（第一条改造）

日期：2026-10-19
范围：签名服务（ota-signing-service）的调用方身份、发布授权与内容策略。

## 1. 改造前的问题

签名服务只做了一件事：收到字节就用私钥签。它不关心：

- 谁在调用（任何能访问 `ota-internal` 的容器/进程都能调）；
- 这次发布是谁批准的（没有发布授权概念）；
- 签的字节是不是被批准的那次发布（可以签任意 JSON）。

因此"私钥在独立容器里"只做到了**密钥位置隔离**，没有做到**签名权限隔离**：
攻破 ota-api 或任何一个内网容器，就能用生产密钥签任意升级包。

## 2. 改造后的三层边界

```
         运维主机（离线）                         容器网络 ota-internal
 ┌──────────────────────────┐
 │ root.key（离线，不出机）  │
 │   └─ 签发 release 证书    │
 │ release.key（离线）       │           ┌──────────────────────────┐
 │   └─ 签发 grant           │  grant    │ ota-api                  │
 │ scripts/15-release-...py  │──────────▶│  只读挂载 active.json    │
 └──────────────────────────┘           │  无 release 私钥         │
                                        └────────────┬─────────────┘
                                                     │ HMAC-SM3 服务身份
                                                     │ + grant + manifest
                                                     ▼
                                        ┌──────────────────────────┐
                                        │ ota-signing-service      │
                                        │  root.pub（只读）        │
                                        │  release 证书（只读）    │
                                        │  signing.key（唯一持有） │
                                        │  SQLite：nonce/配额/幂等 │
                                        └──────────────────────────┘
```

### 2.1 服务身份（调用方是谁）

每个调用方一个 HMAC-SM3 密钥文件（`pki/service-auth/<service>.key`，0600），
权限范围登记在 `pki/service-auth/identities.json`。

请求头：

```
X-OTA-Service:   ota-api
X-OTA-Timestamp: 1789...
X-OTA-Nonce:     <32 hex，一次性>
X-OTA-Signature: HMAC-SM3(secret, METHOD\npath?query\ntimestamp\nnonce\nSM3(body))
```

校验规则：

- 时间窗 ±90 秒；
- nonce 在 SQLite 唯一约束下去重（4 个 gunicorn worker 共享同一份真相）；
- 签名绑定 method、完整 path（含 query）、时间戳、nonce 和请求体摘要；
- 身份必须拥有该接口要求的 scope。

`/sign-manifest` 需要 `manifest:sign`，`/verify` 需要 `manifest:verify`，
`/ecu_keygen`、`/verify_device_pop` 需要 `ecu:provision`，`/sm2_encrypt`
需要 `ecu:wrap`，`/sign_time` 需要 `time:attest`。当前只有 ota-api 一个身份。

### 2.2 发布授权（这次发布被谁批准）

发布授权是另一把密钥，不是签名密钥：

- `pki/release-v1/release.key`：离线保存，只在运维主机上签发 grant；
- `pki/release-v1/release.cert.json` + `.sig`：root 用 `-id ota-root-v1`
  签发的密钥证书，声明 role=`release-authority`；
- 签名服务只信任 root 公钥验证通过的证书，证书里的公钥再验证 grant。

grant 由 `scripts/15-release-authorize.py issue` 生成，绑定：

| 字段 | 含义 |
|---|---|
| `auth_id` | 授权唯一 ID（32 hex） |
| `release_key_id` | 必须是 `ota-release-v1` |
| `not_before` / `not_after` | 授权有效期 |
| `max_tasks` | 最多允许签多少个任务（配额） |
| `package_id` / `version` / `min_version` | 发布身份 |
| `rollback_index` | 防回滚基线 |
| `size` / `sm3` / `encrypted_size` / `encrypted_sm3` | 包内容摘要 |
| `sm4_iv` / `chunk_size` | 加密与分块参数 |
| `ecu_type` / `component` / `vehicle_models` | 适用对象 |
| `expires_at` | 包本身的过期时间 |
| `key_id` | 本次发布允许使用的签名密钥 |

grant 被篡改、签名者不是 release 密钥、过期、密钥已被撤销，任何一条都拒绝。

### 2.3 内容策略（签的字节是否就是被批准的发布）

`manifest` 必须**恰好**包含 19 个字段，多一个少一个都拒绝：

- 不可变 15 项：与 grant 逐项严格相等；
- 可变 4 项：`task_id`、`vin`、`issued_at`、`wrapped_key`，做格式与时间窗校验；
- VIN 必须匹配 `^[A-HJ-NPR-Z0-9]{17}$`；
- `task_id` 幂等：同一 `(auth_id, task_id)` 重复请求返回第一次的签名，不重复扣配额；
- 配额在 SQLite 中用 `BEGIN IMMEDIATE` 原子扣减，多 worker 不会超发。

签名密钥状态从只读挂载的 `data/trust/trust-metadata.json` 读取，**只有
`status=active` 才允许签名**（验签仍允许 `active/deprecated`，以兼容轮换过渡期）。

## 3. 接口变化

| 接口 | 改造前 | 改造后 |
|---|---|---|
| `/sign` | 任意字节签名 | **已移除（404）** |
| `/sign-manifest` | 不存在 | 需服务身份 + grant + 内容核对 |
| `/verify` | 无鉴权 | 需 `manifest:verify` |
| `/pubkey/<id>` | 无鉴权 | 需 `pubkey:read` |
| `/ecu_keygen` | 无鉴权 | 需 `ecu:provision`，不再返回口令 |
| `/verify_device_pop` | 无鉴权 | 需 `ecu:provision`，VIN 格式校验 |
| `/sm2_encrypt` | 任意长度 | 只允许 16 字节内容密钥 |
| `/sign_time` | 无鉴权 | 需 `time:attest`，nonce 长度/字符集校验 |
| `/health` | 列出密钥 ID | 只返回数量与 `raw_signing_enabled=false` |

ota-api 侧：

- 所有对签名服务的调用走 `services/ota-api/svc_client.py`，身份密钥从文件读取；
- `/request-task` 先读 `data/release-grants/active.json`，用 grant 里的 `key_id`
  作为本次发布密钥；若与 trust 的 active key 不一致，返回 503
  `release_grant_key_not_active`（轮换后必须重新发布授权）；
- `/admin/rotate-trust` 增加 `X-Admin-Token`，令牌文件 0600，车辆与服务身份都拿不到。

## 4. 运维流程

```bash
# 首次/轮换后签发发布授权（离线，需要 release 私钥）
scripts/15-release-authorize.py issue --key-id ota-signing-v2 --max-tasks 1000

# 查看当前票据与配额
scripts/15-release-authorize.py show
scripts/15-release-authorize.py status

# 撤销一张票据（签名服务立即拒绝）
scripts/15-release-authorize.py revoke --auth-id <32hex>
```

密钥轮换的完整顺序：

1. 管理接口把新密钥置 `prepared`；
2. `auto_rotate`：旧密钥 `deprecated`、新密钥 `active`；
3. 宽限期结束，旧密钥转 `revoked`；
4. **用新密钥重新签发 grant**（新发布必须有新授权）；
5. 新 grant 生效后，旧 grant 即使还在有效期内，也会因
   `key_not_active` 被拒。

## 6. 残余风险（下一步）

1. grant 目前是"包 + 配额"级授权，不是逐 VIN 白名单。被攻破的 ota-api
   仍可在配额内为任意 VIN 申请签名（但无法跨车投放，车端校验 VIN）。
   建议给 grant 增加可选 `vin_allowlist` 或批次清单。
2. 签名服务读取的 trust 元数据由 ota-api 可写。虽然管理接口已加令牌，
   被攻破的 ota-api 仍可改密钥状态（例如把旧密钥改回 active，从而使用
   仍在有效期内的旧 grant）。建议把"签名密钥策略"拆成独立文件，只由
   运维 CLI 写，ota-api 只读。
3. 私钥仍在文件系统，口令文件与私钥同容器。生产应迁移到 HSM/KMS，
   签名服务只持有句柄。
4. 服务间仍是明文 HTTP，HMAC 防篡改但不防窃听/重放窗口内的流量分析。
   生产建议 mTLS。
5. release 私钥目前在运维主机文件系统，未进 HSM；建议双人授权 + 离线签名机。
6. `/admin/devices`、`/admin/summary` 仍是只读且无鉴权；接口若暴露会泄露
   VIN 清单与密钥池规模，交付时应与 `/admin/rotate-trust` 一起置于管理网络。
